# December 9, 2025 - GitHub Actions Mirror Workflow

Time: ~2:15min

## Overview
Successfully set up automated repository mirroring between a private repository and a public mirror using GitHub Actions. This workflow automatically force-pushes changes from the private repo to the public mirror whenever changes are pushed to the `development` branch.

## Repositories
- **Private (Source)**: `Maximus-Technologies-Uganda/empty`
- **Public (Mirror)**: `Maximus-Technologies-Uganda/caleb-training-mirror`
- **Synced Branch**: `development`

## Workflow Configuration
Created a GitHub Actions workflow (`.github/workflows/on_push_to.yml`) that:
- Triggers on push to the `development` branch
- Uses SSH authentication via deploy key for secure pushing
- Force-pushes changes to maintain an exact mirror
- Includes verification step to confirm successful sync

### Key Components
1. **Authentication**: SSH deploy key stored as `MIRROR_DEPLOY_KEY` secret
2. **Push Strategy**: `--force` to ensure mirror always matches source exactly
3. **Verification**: Automated SHA comparison to confirm sync success

## Challenges & Solutions

### Issue 1: Force-with-lease Rejection
**Problem**: `--force-with-lease` failed with "stale info" error because the workflow hadn't fetched the remote branch state first.

**Solution**: Changed to `--force` since this is a true mirror workflow where the target should always match the source, regardless of remote state.

### Issue 2: Syntax Error in Verification
**Problem**: Extra space in the test command would cause verification to fail.

**Solution**: Fixed syntax: `$(git rev-parse ${{ env.MIRROR_BRANCH }}-mirror)` (removed trailing space).

## What I Learned
- How to configure GitHub Actions workflows with triggers and jobs
- SSH authentication in CI/CD using deploy keys
- The difference between `--force` and `--force-with-lease` for git push
- How to troubleshoot workflow failures using GitHub Actions logs
- The importance of `persist-credentials: false` when mixing HTTPS and SSH authentication
