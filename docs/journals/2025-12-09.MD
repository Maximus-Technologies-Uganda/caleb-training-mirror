## 5. Bugs & Fixes

### Bug 1: Force-with-lease Rejection (GitHub Actions)
**Symptom**: `--force-with-lease` failed with "stale info" error  
**Root Cause**: Workflow hadn't fetched remote branch state before pushing  
**Fix**: Changed to `--force` since this is a true mirror where target should always match source

### Bug 2: Boolean Flag Not Working (Hello CLI)
**Symptom**: Both `--false` and `--true` flags produced uppercase "HELLO" output  
**Root Cause**: `process.argv[3]` returns a string; any non-empty string (including `"false"`) is truthy in JavaScript  
**Fix**: Changed from value-based flags to presence-based `--shout` flag (standard CLI convention)

### Bug 3: Jest Not Found in CI
**Symptom**: GitHub Actions failed with `sh: 1: jest: not found`  
**Root Cause**: Jest was installed locally but not listed in package.json devDependencies; `npm ci` didn't install it  
**Fix**: Added `"jest": "^29.7.0"` to devDependencies and updated package-lock.json

### Bug 4: Files Missing After Branch Switch
**Symptom**: CLI files disappeared after switching from feat/hello-cli to development  
**Root Cause**: Files created on feature branch don't exist on other branches until merged  
**Fix**: Proper branch awareness and git stash workflow to move changes

## 6. What I Learned

### GitHub Actions & CI/CD
- How to configure GitHub Actions workflows with triggers, jobs, and steps
- SSH authentication in CI/CD using deploy keys stored as secrets
- The difference between `--force` and `--force-with-lease` for git push
- `persist-credentials: false` is crucial when mixing HTTPS checkout with SSH push
- `npm ci` is stricter than `npm install` and requires proper package.json

### JavaScript & CLI Development
- **JavaScript truthy values**: Any non-empty string is truthy, including `"false"` and `"0"`
- **CLI conventions**: Presence-based flags (`--flag`) are standard for booleans, not value-based (`--flag=true`)
- **Exit codes**: 0 = success, 1 = error; critical for scripting and automation
- **Error output**: Error messages go to stderr, not stdout

### Git & Branch Management
- Files created on feature branches don't exist on other branches until merged
- `git stash` is useful for moving uncommitted changes between branches
- Local node_modules can mask missing package.json dependencies
- CI environment is clean and exposes configuration issues that work locally

### Testing & Documentation
- Test coverage should include both positive and negative cases
- Error handling should provide clear messages and usage instructions
- Documentation should include usage examples AND error cases
- Review packets help capture learning and debugging process

### Test-Driven Development (TDD)
- **Write tests first**: Clarifies requirements and expected behavior before implementation
- **Red-Green-Refactor cycle**: Write failing test → Make it pass → Improve code
- **Comprehensive coverage**: Writing tests first naturally leads to better edge case coverage
- **Async testing in Jest**: Use `done()` callback for time-based operations
- **Test organization**: Group related tests with `describe()` blocks for better readability

### Clean Architecture
- **Pure core modules**: Separate business logic from I/O for testability
- **Thin wrappers**: CLI/UI layer should be thin and delegate to core logic
- **State management**: Simple boolean flags with clear transitions prevent invalid states
- **Dependency direction**: Core module has zero dependencies; wrappers depend on core

## Reflection

**Most Valuable Learning**: Understanding that local development can hide configuration issues that only appear in CI. The jest dependency issue was a perfect example - it worked locally because jest was in node_modules, but CI exposed that it wasn't properly declared in package.json.

**Best Debugging Moment**: Discovering the boolean flag bug by testing both `--false` and `--true` and getting identical results. This led to understanding JavaScript's truthy values and learning proper CLI flag conventions.

**TDD Experience**: The stopwatch implementation was my first true TDD experience. Writing tests first felt awkward initially, but it resulted in:
- Better code design (had to think about API before implementation)
- More comprehensive test coverage (20 tests vs 4 in hello CLI)
- Faster debugging (tests caught issues immediately)
- Higher confidence in code correctness

**Architecture Growth**: The progression shows clear evolution in design thinking:
1. **Hello CLI**: 1 function, 4 tests, simple implementation
2. **Stopwatch**: Class-based design, 20 tests, pure core + thin wrapper, 155 lines of documentation
3. **Temperature**: Pure functions, 24 tests, stateless design, comprehensive validation

**Pattern Recognition**: After three TDD implementations, the process is becoming natural:
- Tests written first without hesitation
- Edge cases identified before coding
- Design decisions driven by testability
- Confidence to refactor based on test suite

**Time Management**: Tasks took longer than estimated, but the investment in TDD, clean architecture, and thorough documentation pays off in maintainability and learning depth. Total: 9 hours across 4 major PRs.
